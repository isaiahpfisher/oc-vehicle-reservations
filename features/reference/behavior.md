# Behavior & Rules Reference


**Living snapshot** of product rules currently in force. Feature 2 area rules, Feature 3 role rules, Feature 4 vehicle type rules, Feature 5 vehicle rules, Feature 6 destination rules, Feature 7 driver rules, Feature 8 vehicle request rules, Feature 9 mileage log rules, Feature 10 issue report rules, Feature 11 maintenance need rules, Feature 12 service type rules, Feature 14 note rules, Feature 15 vehicle type instruction rules, and Feature 18 vehicle status rules are recorded here.

These files answer: *"What rules does the app enforce right now?"*  
They do **not** authorize new scope — implement only from `features/feature-*.md`.

|------|------|

## Authentication

| Rule | Enforcement | Provenance |
| ---- | ----------- | ---------- |
| Sign-in uses a Google ID token | `POST /api/login` body is `{ googleCredentials }`. The server reads email and name from the verified token. | Feature 1, FR-001, FR-006 |
| Stored name follows Google | Every successful login writes `given_name` and `family_name` onto the user. No API changes `firstName`, `lastName`, or `email`. | Feature 1, FR-006; Feature 3 |
| Only OC emails can sign in | The domain must be `oc.edu` or a subdomain such as `eagles.oc.edu`. Any other verified email returns `401` `{ "message": "Non OC email used." }` and creates nothing. | Feature 1, FR-006 |
| Only sign-in creates users | A new verified email creates a user on login. No endpoint creates users. | Feature 3, FR-013 |
| Development sign-in | With `DEV_LOGIN=true` (never in production), `POST /api/dev-login` signs in as an existing user with the shared `DEV_LOGIN_PASSWORD`. The login page shows the form only in development builds. `npm run seed` loads test users for every role. | Feature 3, FR-014–FR-016 |
| Session is an app JWT for 24 hours | Stored in `sessions` and `localStorage` key `user`. Later calls send `Authorization: Bearer`. An unexpired session for that user is reused. | Feature 1, FR-002, FR-003 |
| Opening `/` without a session redirects to login | Router guard. A stored session that opens `/login` redirects home. | Feature 1, FR-005 |
| Sign out deletes that session | `POST /api/logout` deletes the matching session row and the client removes `user`. | Feature 1, US-1.4 |
| `authenticate` sets `req.user` | Bearer token must match an unexpired session row. `req.user` is `{ id, roles }`, loaded from the database on every request. | Feature 1, FR-004; Feature 3, FR-009 |
| No profile editing | The avatar menu shows name, email, and **Sign out** only. | Feature 3 |

## Areas

| Rule | Enforcement | Provenance |
| ---- | ----------- | ---------- |
| Any signed-in user can list areas; only admins manage them | `GET /api/areas` and `GET /api/areas/:areaId` use `authenticate`. `POST`, `PUT`, and `DELETE` use `authenticateAdmin` (`403` otherwise). `/areas` has `meta.roles: ["admin"]`, so non-admins don't see the **Areas** link and are redirected home. | Feature 2, FR-001; Feature 3, US-3.6 |
| Name is trimmed, required, unique, and at most 255 characters | Empty or whitespace-only name returns `400` `{ "message": "Missing name." }`. A longer name returns `{ "message": "Name too long." }`. A name already stored on a different area returns `{ "message": "Name already taken." }`. Saving an area with its own current name is allowed. | Feature 2, FR-002, FR-004 |
| Logo is a URL or an empty string | The stored value is trimmed. `""` is stored when the logo is omitted or blank. A JSON `logo` of `logo.png` returns `400` `{ "message": "Invalid logo URL." }`. A non-empty logo must be an `http` or `https` URL. An uploaded file must be `.png`, `.jpg`, `.jpeg`, or `.webp` and at most 2 MB. Anything else is `400` `{ "message": "Unsupported file type." }` or `{ "message": "File must be under 2 MB." }`. The file is stored in the public bucket `area-logos` at `{AREA_LOGO_PREFIX}/{areaId}/{filename}`. Each developer sets their own prefix. Production uses `prod`. The areas list renders that image, 40px tall, and the filename, only when `logo` is not empty. A failed upload is `500` `{ "message": "Failed to upload logo." }` and the saved logo does not change. Replacing, clearing, or deleting the area removes that area's files only. The prefix folder stays. `reset-local-data` stops the backend, deletes that folder and recreates it, and drops and recreates the databases named by `DB_NAME` in `backend/.env` and `backend/.env.test`. The browser never receives the Supabase key. | Feature 2, FR-005, FR-006; Feature 17, FR-001, FR-002, US-17.1, US-17.2, US-17.3 |
| Delete removes the area when it has no vehicles | `DELETE` returns `200` and deletes the area's `area_admin` roles with it, and the objects under `area-logos/{AREA_LOGO_PREFIX}/{areaId}/`. If the area still has vehicles, `DELETE` returns `400` `{ "message": "Area has vehicles. Delete vehicles or reassign them to a different area first." }` and the area stays. | Feature 2, Assumptions; Feature 3; Feature 5, FR-026; Feature 17, US-17.3 |
| Areas are managed on one screen | `/areas` heading is **Area Management**. The list is a table. **+ New Area** opens a dialog with **Name** and **Upload logo**. After a file is chosen the button reads **Remove File** and the filename is shown. The logo image is the first cell in each row. The filename, upload icon, and remove icon stay in the Logo column, and those icons stay in the same place whether or not the row has a logo. The remove icon is grayed out when that row has no logo. Edit is inline. Choosing a file or removing it takes effect on **Save**. Delete uses the shared confirmation dialog. Empty list copy is **No areas yet. Create your first area.** | Feature 2, Screen Requirements; Feature 17, Screen Requirements |

The identifier label is **VIN** until a `Serial` type is selected. | Feature 5, Screen Requirements; Feature 18 |

## Vehicle status

| Rule | Enforcement | Provenance |
| ---- | ----------- | ---------- |
| Status is worked out, not stored | `condition` is computed on every vehicle read by `helpers/vehicleStatus.js`, the one place these rules live. Only admins, area admins (their areas), and maintenance users can read it. | Feature 18, FR-001, API Requirements |
| One status per vehicle | First that applies: **Retired**, **Out of Service** (an Open or In Progress maintenance need marked out of service), **Service Overdue**, **Plate Expired** (expiration date before today; none is never flagged), **Service Due Soon** (500 mi or 14 days or fewer), **Plate Expiring** (still good, but expires within 30 days, today included; "License plate expires tomorrow (Nov 24, 2026)."), **Available**. Issue reports never change status. | Feature 18, FR-002, Assumptions |
| Estimated mileage | Latest mileage log by recorded date (then id) plus the estimated miles of trips that ended, weren't cancelled or denied, and started after that date. Unknown trip miles add 0. With no logs it starts at 0 (vehicles have no initial-mileage column). | Feature 18, FR-003, Assumptions |
| Service due | Each service type is due at the last service log of that type (its mileage log reading and date) plus the type's frequencies, whichever comes first. Never serviced counts from purchase date and 0 miles. A type with no frequencies is never due. Overdue once past the due mileage or date. | Feature 18, FR-004 |
| Only usable vehicles can be assigned | `PUT /api/requests/:id` with `vehicles` returns `400` for a newly added vehicle that is retired, out of service, or booked by another request that isn't cancelled or denied and overlaps the trip. Vehicles already on the request are never rejected. Feature 8 used to allow booked vehicles with a flag. | Feature 18, FR-005; Feature 8, US-8.8 |
| Service and plate problems are warnings | Service due by the trip's last day, or estimated trip miles passing the due mileage (date only when miles are unknown), and a plate that expires before the trip's last day are flagged but can be assigned. | Feature 18, FR-006 |
| Driver license warnings | On a request, a driver whose license expires before the trip's last day is flagged for managers. | Feature 18, FR-007 |
| Problems show only while they matter | `vehicleProblems` / `driverProblems` go to the request's managers only, and are empty unless the request is pending, awaiting vehicle, or reserved and its trip hasn't ended. | Feature 18, US-18.9, US-18.10 |
| Vehicle list filters | One row with a **Status** select, a **Filters** button, and **Needs attention**, like the request list. **Filters** opens a panel with Type, Make, Model, Color, and Year selects (choices come from the listed vehicles) and **Clear filters**; its badge counts the panel's active filters. **Needs attention** (Out of Service, Service Overdue, Plate Expired, Service Due Soon, Plate Expiring) with a count, and **Clear filters**. Changing a filter returns to page 1. No match shows **No vehicles match these filters**. Hovering a status chip lists why. Maintenance users see **View vehicle** only. | Feature 18, US-18.2, US-18.13 |
| List search rows | Every list's search and filters use the same row: compact outlined fields and 40px buttons that wrap. Record names in tables are links in the theme color, underlined on hover. |
| Sidebar | A page outside its link's path names its link: a vehicle's service log marks **Vehicles**; Profile marks nothing (it used to fall back to My Requests). |
| Vehicle page | Styled like the driver form (`FormSection` groups: Assignment, Identity, Description, Registration). Above it, a **Status** card: the status chip; tiles for **Estimated mileage** (with how it was worked out), **Next service**, **Upcoming trips**, and **License plate** (red once expired); a retired vehicle hides its service schedule; out-of-service needs (linked) only when there are some; a **Service schedule** sorted most urgent first that shows only overdue and due-soon services until **Show all**; and the first 3 upcoming trips (linked for managers) with **Show N more**. Below it, the 5 latest mileage readings and the 5 latest service visits (one row per visit, naming its services) with **View all** links, **+ New Mileage Log**, and **+ New Service Log**; a snackbar confirms a new log. Maintenance users can add both but can't edit the vehicle. Saving a change to **retired** while the vehicle has upcoming trips first asks **Retire vehicle** and lists up to 5 of them. | Feature 18, US-18.3, US-18.12 |
| Assign dialog | Lists every vehicle in the area, retired included. Retired, out-of-service, and booked vehicles are disabled with the reason, unless already assigned (then **Assigned, but now unavailable: …**, and they can be removed). Problems show one line and one chip per kind; several services due become one line (**3 services due before the trip ends: …**) with every message on hover. The subtitle shows `service in N mi or by <date>`. **Available on these dates** hides blocked vehicles; **Not due for service** hides vehicles with service due before the trip ends. | Feature 18, US-18.6–US-18.8 |
| Request page and list warnings | Each vehicle with problems gets one warning under it in the Vehicles card, a line per kind of problem; each driver with a license problem gets one in the Drivers card. The admin request table shows a warning icon next to the vehicles of flagged requests; hovering lists each vehicle's problems. The week and month calendars put a small warning mark before a flagged trip's name (in the event's text color; hovering lists the problems), and the key adds **Vehicle problem** when one is showing. **Vehicle problems** filters to them. | Feature 18, US-18.9, US-18.10 |
| Maintenance need form | Vehicle choices show their status chip. With a vehicle chosen, Out of Service **Yes**, and status Open or In Progress, a card with a warning edge says **Booked for N upcoming trips** and lists the first 3 (purpose, dates, area, status) with **Show N more**. Admins and the trip's area admins can open each trip's request in a new tab; maintenance users see the purpose as text. | Feature 18, US-18.11 |

## Roles

| Rule | Enforcement | Provenance |
| ---- | ----------- | ---------- |
| Roles are `admin`, `area_admin` (per area), `maintenance` | `roles` rows; everyone also has requester permissions. A user can hold several roles but not the same one twice. | Feature 3, FR-002, FR-003 |
| Admins pass every role check | `authorizeRoles` and `useRoles().hasAnyRole()` both treat `admin` as holding every role. `hasRole()` does not (display only). | Feature 3, FR-004, FR-010 |
| Role failures are `403` | Role middleware returns `403` with a role message; missing/invalid sessions stay `401`. | Feature 3, FR-010 |
| Only admins manage users | `GET /api/users`, `PUT` and `DELETE /api/users/:id` require `admin`. Non-admins may `GET` only themselves (others → `404`). | Feature 3 |
| Admins cannot lock themselves out | An admin cannot remove their own `admin` role or delete themselves (`400`; the UI blocks or disables it first). | Feature 3 |
| Roles are replaced atomically | `PUT /api/users/:id` swaps the full role set in one transaction. | Feature 3, FR-012 |
| First admin comes from a script | `npm run make-admin -- <email>` in `backend/` grants `admin` to an existing user and leaves that user's other roles. No API does this. | Feature 3, FR-008 |
| Role scripts replace every other role | `npm run make-maintenance -- <email>` leaves only `maintenance`. `npm run make-requester -- <email>` removes every role row. `npm run make-area-admin -- <email> <area>` leaves only `area_admin` for that area name or id. An unknown email or area changes nothing. | Feature 3, FR-018 |
| Routes declare `meta.roles` | The user needs any listed role (admin always passes); no `meta.roles` = any signed-in user. The router guard and MenuBar links use the same `canOpen()` check. Routes open without a session (login) declare `meta.public`. | Feature 3, FR-011; Feature 1, FR-005 |
| Frontend refreshes roles per page load | The first navigation after a page load calls `GET /api/users/:id` and replaces the stored roles before any role check. A `401` clears `user` and goes to login. | Feature 3, FR-009 |
| Users list | Admin-only table at `/users`: name, email, role chips (`Admin`, `Maintenance`, `Area Admin — <area>`), 10 per page, name search (case-insensitive) and role filter; changing either returns to page 1. | Feature 3, US-3.1–3.3 |
| User details | `/users/:id`: header with name, email, role chips, and member-since date; **Access** card with checkboxes (System roles; Area admin of, one per area) and its own Save/Cancel that stay on the page; **Driver** card shows the linked driver's status, license state and expiration, and phone number, or **No linked driver.**; **Requests** / **Issue reports** / **Maintenance** (maintenance users only) tabs show "Coming soon" until Features 8–13; **Account** card deletes the user. On your own page, Admin and Delete are disabled. | Feature 3, US-3.4, US-3.5; Feature 7, FR-020 |
| Delete user | Confirm dialog naming the user, from the users list or the details page; disabled for the admin's own account. A linked driver is kept with no linked user. | Feature 3, US-3.5; Feature 7, FR-017 |
